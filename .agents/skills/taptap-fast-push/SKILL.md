# 快速提交与推送

目标是让**准备好交付后的 Git 阶段**通常在两分钟内完成，不把开发、冲突整合、打包、上传大资源或网络等待伪装成两分钟承诺。

先按根 AGENTS 读取当前入口和自己任务相关的最新交接。ACTIVE_WORK 很长时读取顶部及自己模块对应条目，不重复输出整份历史；需要指定技能时仍完整读取所选技能及其必读说明。

## 提交就绪检查

- 确认 Unity 仓库、origin、当前分支及工作树归属。worker 沿用 `taptap-git-worker` 权限，只推自己的分支；用户授权的当前整合者才能合并及推 main。
- 只显式暂存本任务文件，包括必要的 `.meta`、配套规划和功能说明。不要 `git add .`，不要清理、stash 或覆盖他人工作。
- 验证与风险匹配：文字修订不启动 Unity；已有同一源码/资源版本的成功编译或测试可复用。只改交接说明后不重复打包。Runtime/SDK 改动仍需对应编译和专项验证，不能为了达标省略未做的验收。
- 关卡按正式交付规范成套提交；现有 pre-commit hook 已运行规划守卫时，不再手动重复同一检查。需要实际布局或绑定核对时不能只靠配对守卫。
- 检查暂存列表及 `git diff --cached --check`，确认没有 Secrets、Token、密钥、Library/Temp/Logs/Builds 或用户本地设置。查看实际 diff，尤其注意大场景是否混入无关生成变化。

## Git 阶段

记录开始时间；完成一次必要的 fetch，确认目标分支关系，然后 commit、非强制 push。已经取得的同轮远端信息无需逐步重复 fetch 或枚举全仓库历史。分叉/冲突停止并报告，不自动 rebase、改写历史或关闭 hook。

超过两分钟时指出当前具体瓶颈：例如冲突等待、pre-commit 检查、Git 压缩还是网络传输；不要继续扩大到无关全项目扫描。资源量异常时先查看本次待推对象和文件大小，不因猜测擅自改 LFS、压缩源图或删资源。

交付给出分支、SHA、实际推送是否成功、耗时及已验证/未验证项。不要把本地 commit 当成推送成功。发布打包是独立任务，不默认加入每次普通推送。
