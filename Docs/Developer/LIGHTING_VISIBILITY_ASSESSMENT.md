# 光照与墙体遮挡可见性评估

2026-10-20 更新：已按第三种方案实现可选二维遮挡光照并完成隔离 GPU/Play 验证，操作与限制见 [二维遮挡光照与喷泉](WORLD_VISIBILITY_AND_FOUNTAIN.md)。下面保留实施前评估，不代表本轮切换了2D/3D渲染器或已验收手机性能。

## 结论

当前项目不适合直接把全套表现切到常规2D或3D光照。更稳妥的是保留现有URP、像素美术和颜色解锁链路，增加独立的二维“光照／可见性遮罩”：按实际墙体轮廓阻挡玩家光源，再与世界画面合成。不是按房间ID整块点亮，也不是把已有圆形转场遮罩直接搬过来。

这不是Unity做不到，而是项目现在的渲染材料、玩法物理和美术层级并非同一种标准光照管线。以下为2026-10-19源码检查结果，不代表已实现或做过真机性能验收。

## 当前项目直接加灯会发生什么

- Unity6000.3.12f1，URP17.3；PC和Mobile默认使用Universal Renderer，Gaming相机随默认Renderer。项目虽有其他Renderer配置，不等于当前主画面已使用2D Renderer。
- 玩家、世界道具、网格美术、墙地贴图等主要使用自定义Unlit或只采样纹理的Shader。“UniversalForward”标签本身不意味着计算灯光。因此加Point Light不会让这些画面自动变成“亮处可见、暗处看不见”。关闭环境光也不会让Unlit变黑。
- 美术图层已有可选3D Lit模式，但不是全项目通用光照方案；生成美术Renderer当前关闭投影且不接收阴影。玩法墙体主要是3D碰撞／几何，装饰另有Z深度和视差。
- Mobile配置当前没有开启附加灯阴影。单纯在玩家身上挂3D点光源，不能据此保证安卓得到期望的遮挡阴影。开启后也需实测阴影成本、像素图与透明物体的效果。
- 已有水下画面捕获、选择性HSV、像素／故障等渲染处理；还有透明道具、能力连线和粒子。增加后处理或更换Renderer必须明确合成顺序，不能只确认白墙能挡灯就算完成。

## 三种可选路线

| 路线 | 优点 | 本项目的主要代价 |
| --- | --- | --- |
| URP 2D Light + ShadowCaster2D | 官方成熟体系，有形状灯、法线和二维阴影工具 | 需要适配2D Renderer与受光材质，维护二维遮挡轮廓，回归现有水与HSV等功能 |
| 标准3D灯与阴影 | 现有实体墙几何能参与；适合确实需要三维明暗的物件 | 主要像素材质需要改造；透明片、不同Z层和手机附加灯阴影需要统一策略，容易偏离平面像素美术 |
| 独立二维可见性遮罩 + 风格化光照合成 | 保留现有材料与色彩，直接满足“墙后黑、视野内可见” | 要正确提取／缓存遮挡轮廓、处理动态门和移动物体，并接好渲染顺序 |

推荐第三种为主，少量重点物件以后再用法线／真实灯光补质感。官方2D灯并非物理光照，阴影也需要ShadowCaster2D等配置，并非任意3D Collider自动阻光。[Unity 2D灯说明](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/Lights-2D-intro.html)、[二维阴影](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/2DShadows.html)。

## 推荐实现结构

1. 从玩法实体提取世界XY遮挡线段。静态墙合并共享内边、保留孔洞；关门加入，开门移除。不能把一整块合并墙的包围盒当实心，否则通道也会被误封。
2. 玩家光源在附近线段上计算可见性多边形，绘到可复用的低分辨率遮罩，再加距离衰减。成熟方案是端点角度事件／扫描或稳健的可见性多边形实现；不是每帧对全场景所有物体暴力射线。可参考[Red Blob可见性算法与实现注意事项](https://www.redblobgames.com/articles/visibility/)。
3. 静态遮挡按区块缓存，动态门等独立更新；使用空间索引、复用数组和纹理。只在相关位置／轮廓变化时更新，避免全地图重建和大量分配。实际帧预算要在安卓上测，不能只看编辑器。
4. 遮罩作用于世界内容，包括本来不受灯光的精灵、粒子和能力连线；正常HUD与菜单不变黑。与水捕获、HSV和转场明确先后关系，避免黑区仍泄露连线或粒子位置。
5. 相机与视觉遮罩在一致的渲染时序更新，不用FixedUpdate驱动鼠标／画面跟随。世界位置保持连续，不为像素效果量化玩家物理位置；美术对齐仍以16有效像素／世界格为基准。

格子阴影投射也很成熟，例如[Symmetric Shadowcasting](https://www.albertford.com/shadowcasting/)，但更适合离散格视野；本项目有连续移动、门和平台，若直接逐整格显示容易跳变。GPU阴影贴图／SDF可用于更多光源，但实现和移动端填充成本更复杂，不建议作为首版起点。

市面上也有二维光照／视线插件，例如[Smart Lighting 2D](https://assetstore.unity.com/packages/tools/particles-effects/smart-lighting-2d-112535)。它是候选而非已验证推荐：必须先确认Unity6000.3、URP17.3、当前渲染功能、安卓及离线比赛要求，不能仅凭“支持URP”就直接采购或整项目迁移。

## 视觉与玩法边界要先定好

- 默认让实体墙、关闭的门阻光；水、雨、绳子、收集品不阻光。平台、方块、植物是否阻光提供明确策略。携带物不能挡住整个玩家光源导致周围全黑。
- 玩家光建议中性白光，岩浆／能力只做克制的彩色点缀，避免红光把蓝绿机关的辨色规则破坏，或发光让尚未解锁颜色提前显色。
- “有灯照到”与“玩家能看到”不是同一件事：若远处另有光源，是否允许隔墙看见它照亮的房间？若不允许，最终可见区域还要与玩家视线相交。
- 纯黑盲区会改变跳跃、地刺和机关预判难度。建议先做可调微弱环境底色与边缘衰减，再决定哪些区域完全黑。
- Bloom、发光贴图、SSAO、烘焙光照、Occlusion Culling都不能单独代替动态墙体可见性。软化遮罩也要防止光越过薄墙泄漏。
- 不因看不见就关闭物体的物理、机关和房间生命周期；本轮建议仅控制渲染，房间系统仍承担原有重置／索引用途。

## 建议验收顺序

先在隔离测试中做一个玩家光源与墙／门遮挡，测试拐角、窄缝、带孔合并墙、移动相机、玩家贴墙、携带物和房间边界。再接现有水、HSV、粒子与UI。最后扩展少量局部光和画面润色。PC与安卓都应记录CPU/GPU耗时、分配和最差帧；不承诺未经测试的帧率。

本评估未更改Shader、Renderer、项目光照设置或正式关卡。
