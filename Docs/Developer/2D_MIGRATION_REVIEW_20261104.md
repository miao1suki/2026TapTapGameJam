# 2026TapTap 转为长期 2D 项目的全面审查

> 2026-11-05 更新：用户已明确选择原生 2D 全面迁移。下文保留为迁移前的风险审查，原先“暂留 3D 物理”的建议不再作为实施目标。已实施内容、兼容边界和实际验收见 [原生 2D 迁移报告](NATIVE_2D_MIGRATION_20261105.md)。

审查日期：2026-11-04  
审查基线：`main` / `9a68c64`（已先执行 `git fetch origin --prune` 与 `git pull --ff-only origin main`）  
Unity：6000.3.12f1  
审查范围：正式 Gaming 场景、运行时代码、Prefabs、渲染管线、场景编辑器、存档与发布配置。  
本文件只提出迁移方案和验收标准，不修改正式场景、不删除 3D 代码、不重建关卡。

## 结论先行

项目可以转为 2D 长期项目，但建议把“2D”拆成两个层次推进：

1. **立即确定为 2D 产品形态**：锁定正交相机、2D 关卡坐标、2D 美术和 2D 编辑器工作流；保留现有 3D Transform、3D Collider、3D Mesh 作为内部实现。
2. **稳定后再评估 2D 物理迁移**：只在需要降低维护成本或解决性能问题时，按系统逐个替换为 `Rigidbody2D`、`Collider2D`、`SpriteRenderer` 或 Tilemap。

不建议现在直接做“删除所有 3D 组件、改用 Unity 2D Renderer、批量把所有 Rigidbody 改成 Rigidbody2D”。当前游戏不是只用了一点 3D 外壳，而是把 3D 物理、网格、Z 深度、房间重置、光照遮蔽和编辑器工具组合成了完整运行时。一次性删除会同时破坏玩家运动、接触方块、门、单向平台、梯子、移动平台、水体、房间切换、Boss、存档和正式关卡。

推荐目标是：**玩家看到和编辑的是稳定的正交 2D 世界；引擎内部暂时允许使用 3D 实现；所有关卡数据和关系只保留一份权威来源。** 这条路线能最快进入长期维护状态，也保留以后局部转换为真正 2D 物理的余地。

## 一、当前基线和证据

### 1. 仓库状态

本次审查前已拉取远端 `main`，当前 `HEAD` 与 `origin/main` 均为 `9a68c64`。拉取是快进，没有覆盖本地未跟踪文件。工作区当前仍有以下未跟踪内容，它们不属于本迁移报告，也没有被删除：

- `Assets/Plugins/Demigiant/DOTweenPro.meta`
- `Assets/Plugins/Demigiant/DOTweenPro/`
- `Docs/Developer/EDITOR_LAG_ANALYSIS_20261029.md`

后续做迁移分支时，应先决定这些文件是纳入长期项目、加入忽略规则，还是单独归档，不能让它们在迁移提交中被误带进去。

### 2. 正式场景的静态规模

对 `Assets/_Project/Scenes/Playing/Gaming.unity` 的序列化组件标识进行静态统计，当前得到：

| 类型 | 数量 | 说明 |
|---|---:|---|
| `LevelEditorPlacedBlock` | 3008 | 场景中的放置对象组件；包含编辑器和运行时承载信息 |
| `RoomResetObject` | 2854 | 房间进入、重生、读档时的对象重置记录 |
| `LevelEditorMergedShape` | 99 | 合并后的碰撞/形状对象 |
| `RoomLifecycleManager` | 1 | 房间区域、进入退出和重置的核心管理器 |
| `GridArtScene` | 1 | GridArt 运行时与场景的连接 |
| `BossRespawnMarker` | 9 | Boss/场景重生相关标记 |
| `MovingPlatformFeature` | 16 | 移动平台玩法对象 |

这些数字是当前正式场景文件中的组件实例统计，不等同于可见物体数量，也不代表可以直接删除的对象数量。尤其是 `RoomResetObject`，它关系到房间切换和存档恢复，不能因为目标变成 2D 就移除。

### 3. 代码和资源的 2D/3D 现状

静态扫描结果如下。代码命中数是文件命中数，不是运行时实例数：

| 项目 | 当前命中情况 | 判断 |
|---|---:|---|
| `Rigidbody` | 125 个代码/Prefab/场景/资源文件命中 | 现有玩法主要使用 3D 物理 |
| `Rigidbody2D` | 5 个文件命中 | 不是当前主物理方案 |
| `BoxCollider` | 160 个文件命中 | 碰撞主方案是 3D Collider |
| `BoxCollider2D` | 2 个文件命中 | 不能视为已完成 2D 迁移 |
| `PolygonCollider2D` | 0 个文件命中 | 当前没有 2D 多边形碰撞方案 |
| `MeshFilter` | 129 个文件命中 | 大量方块、水体、特效用网格承载 |
| `MeshRenderer` | 141 个文件命中 | 画面仍以网格渲染为主 |
| `MeshCollider` | 21 个文件命中 | 刺、墙和复杂形状仍有网格碰撞 |
| `Perspective3D` | 12 个文件命中 | 相机仍保留可切换 3D 模式 |
| `WorldVisibility2D` | 11 个文件命中 | 名称是 2D，但实现仍依赖 3D 网格、BoxCollider 和 URP |

仓库中没有发现常规 `fbx/obj/blend/dae/glb/gltf` 等导入的 3D 模型文件。美术本身大多是像素 2D，这对转型有利；但“使用 2D 美术”与“使用 Unity 2D 物理/2D Renderer”是两件不同的事。

### 4. 物理和坐标基线

- `ProjectSettings/DynamicsManager.asset` 使用三维重力 `{x:0,y:-9.81,z:0}`。
- `Physics2DSettings` 虽然存在 2D 重力配置，但主玩法并没有改用 2D 刚体。
- `ContactCube`、水柱、移动平台、玩家和很多机制使用 `Vector3`、3D 触发器、`Physics.OverlapBoxNonAlloc` 或三维刚体。
- `Gaming_Art.asset` 仍有不同的 Z 深度，例如背景、墙、玩家前后层使用不同 Z 值。Z 不是可以直接清零的“多余 3D 信息”，它目前承担遮挡和绘制顺序职责。
- 编辑器整改已经把 SceneView 作为新编辑入口，目标是正交 2D 场景编辑；但这项整改并不等于运行时物理已经迁移到 2D。

### 5. 渲染和可见性基线

当前 `Assets/Settings/PC_Renderer.asset` 和 `Assets/Settings/Mobile_Renderer.asset` 仍使用 URP Renderer Feature：

- `WaterUnderlay`
- `WorldVisibility`
- `SelectiveHSV`
- RGB/全屏效果等

`WorldVisibility2D` 只接受正交相机，但它会生成三维 `Vector3` 网格并使用 `BoxCollider` 作为墙体遮挡几何。它不是 Unity 的 `Light2D`，也不能通过切换成 2D Renderer 自动替代。MRoom2、MRoom3 的“不使用光照遮蔽”也属于业务配置，不能在迁移时被一个全局 2D 光照开关覆盖。

## 二、这里的“转为 2D”应如何定义

### 方案 A：2D 产品、3D 内部实现（推荐第一阶段）

表现和工作流全部按 2D 设计：锁正交相机，固定 XY 网格，像素对齐，Z 只作为内部排序；保留当前 3D Rigidbody、BoxCollider、MeshRenderer 和自定义 URP Feature。

优点：改动最小、可以继续使用已验证的 Gaming、Boss、房间重置、移动平台、接触方块、光照遮蔽和移动端包。风险主要是架构仍带有 3D 技术债，但可以用清晰的接口隔离。

### 方案 B：选择性 2D 物理

先把不依赖复杂关系的系统转换为 2D，例如静态墙、普通地面、收集品、简单刺和部分 UI 交互；移动平台、接触方块、水体、房间重置和 Boss 关系暂时保留 3D。两套物理共存时必须定义同步规则，不能让同一对象同时由两个物理系统驱动。

优点：逐步降低 3D 依赖。风险是同一场景中两套碰撞系统容易出现“画面有但不能站”“可以站但触发不到”“重置后引用丢失”等问题。

### 方案 C：完整 Unity 2D 物理和 2D Renderer

统一改为 `Rigidbody2D`、`Collider2D`、`Physics2D`、`SpriteRenderer`/Tilemap、URP 2D Renderer 和 `Light2D`。

这是一次系统重写，不是资源替换。必须重写运动、斜面/梯子/单向平台、抓取与搬运、接触方块、移动平台绑定、水体、墙体遮挡、房间重置、特效深度、测试和编辑器。只有在完成 A 方案并冻结玩法后才值得评估。

### 方案 D：彻底去除所有 3D 概念

包括清除三维 Transform、Z 深度、Mesh、三维 Collider、三维 Renderer 和相关 URP Feature。这会破坏目前的层级顺序、网格水体、遮挡算法和大量现有 Prefab。除非项目要完全换引擎或重做全部玩法，不建议采用。

## 三、按系统逐项审查

### 1. 关卡数据和编辑器

**现状**

正式关卡目前同时存在 Scene、旧规划 JSON、旧地图 JSON、GridArt 和稀疏艺术区域等历史来源。最新编辑器整改已经明确：Scene 中的真实对象、房间和关系应成为唯一权威；PlanningCanvas、规划 JSON、碎片和“应用到场景”只能作为旧数据或导入工具。

**转 2D 必须做的事**

1. 将房间区域统一为正交 XY 网格，集中处理 SceneCell、RegionCell、WorldCenter 和 ArtCell 的坐标转换。
2. 继续保留真实 Scene 对象和真实 Prefab 引用；不要把对象压回 JSON 再重建。
3. 每个放置对象保留稳定作者 ID、所属房间、重置区域、Grid 单元和运行时引用。
4. 对同一格的墙、水、装饰、隐藏块和收集品支持多个通道，不能用“一格只能有一个对象”的旧查找逻辑覆盖它们。
5. 编辑器的打开、关闭、聚焦、切换模式、只读查看必须零写入；只有绘制、擦除、移动、参数、绑定和显式保存才允许产生 Undo 和 Dirty。
6. 区域移动必须同时移动区域格、对象、`LevelEditorPlacedBlock.Cell`、重置归属和明确拥有的艺术层；未声明归属的背景艺术不能被自动吞并。
7. GridArt 采用增量重建和 32×32 受影响区块，打开窗口不能自动重建或写回资源。

**验收**

- 场景编辑器可以在正交 SceneView 完成房间、对象、绑定和艺术编辑。
- 关闭再打开不会改变 Scene、Prefab、JSON、艺术资产、Undo 或版本号。
- 同一格放墙、水和收集品后都可选中、保存、重载并保持图层。
- 区域移动一次 Undo 可完整撤销，房间重置和存档不丢对象。
- 正式 Gaming 试用前，先在隔离测试场景完成全套读写和性能测试。

### 2. 相机和视图

**现状**

`CameraModeController`、`CameraFollowController` 和 `CameraModePanel` 仍保留 `Perspective3D` 模式和相关测试，部分默认配置仍请求透视模式。即使当前正式玩法看起来是 2D，代码仍允许相机切到 3D。

**处理建议**

- 产品层删除 3D 模式按钮、快捷键和运行时入口；先保留内部兼容字段，避免旧存档反序列化失败。
- 将正式相机固定为正交，定义唯一像素对齐规则、参考分辨率、缩放策略和移动端安全区。
- 相机只沿 XY 跟随，Z 和旋转由配置固定；禁止玩法脚本直接改变相机投影类型。
- 过渡动画、Boss 镜头、剧情 Timeline 通过 2D 目标点和正交尺寸完成，不直接依赖透视 FOV。
- 为相机建立“房间边界、镜头边界、引导点、Boss 镜头”数据验证，避免转型后出现镜头穿墙或玩家出屏。

**不要做**：简单把 Projection 改为 Orthographic 后删除相机模式代码。旧存档、Timeline、测试和编辑器可能仍引用这些类型，应该先收敛入口，再逐步清理实现。

### 3. 玩家运动和碰撞

**现状**

玩家使用三维刚体和三维碰撞；重力、地面检测、墙、梯子、单向平台、头顶空间、搬运基座和移动平台都有三维触发关系。之前已出现过基座进两格通道、平台载荷不跟随、梯子图层、玩家悬空等问题，这些都说明碰撞和视觉层不是一个简单的平面切换。

**如果保留 3D 内部实现**

- 将 Z 轴速度和位置锁死，统一由 `Gameplay2DPlane` 或等价约束组件维护。
- 所有碰撞查询使用统一的 XY 投影和 Z 容差，不允许每个系统自行写一套范围。
- 玩家、方块、平台和可搬运基座的碰撞体尺寸必须从像素网格计算，避免不同 Prefab 使用不同单位。
- 继续保留当前 3D 引用和房间重置机制，但把“图层顺序”和“碰撞层”分成两套明确数据。

**如果迁移到 Rigidbody2D**

必须分别验证：斜面/台阶、单向平台、梯子上下、头顶空间、搬运、移动平台载荷、接触方块生长、重力切换、水中浮力、死亡和重生。任何一项没有独立测试，不能替换正式 Prefab。

### 4. 方块、机制和关系

机制关系目前使用真实 Unity 引用，例如门与按钮、移动平台与曲柄/基座、曲柄与制动基座等。长期 2D 项目仍应保留这些强类型引用，不要只依赖坐标或 JSON ID。

迁移时需要：

- 统一 `Bind`、解绑、重载和房间重置时的生命周期。
- 场景移动对象时同步更新关系的空间位置，但不自动改写逻辑归属。
- 任何同格对象都可被准确拾取；拾取和隐藏方块图层不能由渲染顺序决定碰撞。
- 收集品、隐藏块、门、梯子和平台各自拥有稳定的运行时 ID 和重置策略。
- 2D 版本的机制绑定 API 必须与当前游戏逻辑兼容，避免编辑器只能设置视觉而不能设置实际引用。

### 5. 房间、传送、存档和重生

房间管理是长期项目最容易被误伤的部分。它不是 3D 专属，可以完整保留，但要清理重复来源：

1. `RoomLifecycleManager.regions` 是房间区域的权威来源。
2. 传送点只允许进入已解锁的重生点；开启规则、Boss 门槛、钥匙和收集品门槛必须集中在一个可测试服务中。
3. 房间进入和读档时，先恢复区域和对象状态，再初始化可见性、收集品、Boss 和背景音乐。
4. 存档和成就存档的重置按钮必须分别测试；正式包前两者都要清空并记录版本号。
5. Boss 前重生点、Boss 房内重生点、Boss 死亡后状态和读档返回点要用明确状态机，不靠场景加载顺序猜测。
6. 旧存档中没有的新字段要有默认值；迁移不能把旧存档中的稳定收集品 ID 重新生成。

### 6. 美术、图层和深度

项目美术是像素 2D，但当前仍用 MeshRenderer、Transform Z、Prefab 层级和 GridArt。转型要定义：

- 视觉排序：`SortingLayer`、排序顺序还是固定 Z，三选一为主，不允许混用到无法解释。
- 碰撞层：物理层与视觉层独立。
- 房间层：墙、背景、远景、玩家、梯子、收集品、隐藏块、前景遮罩各自声明优先级。
- 像素对齐：相机、物体位置、缩放和贴图采样统一，避免移动时白线、半像素缝和左右描边粗细不同。
- 水、草、泉水、Boss 动画、门和光照遮蔽的材质在正交相机下逐项截图验收。

不建议仅把 `MeshRenderer` 批量改成 `SpriteRenderer`。水体、墙体合并块、接触方块和遮挡图形目前可能依赖动态网格；应先建立等价的 Sprite/Tilemap 或 2D Mesh 方案，再按类型迁移。

### 7. 光照和墙体遮蔽

当前的 `WorldVisibility2D` 是自定义 URP 遮挡系统，不是 Unity 2D 光照。它会生成墙体几何、使用 BoxCollider，并参与 PC/Mobile Renderer Feature。项目要求“玩家只能看到光能到达的房间”，因此光照遮蔽是玩法可见性系统，不能当作普通后处理删除。

建议分三层：

1. **可见性几何**：由墙、门和房间区域生成遮挡边界。
2. **光照衰减**：软边、淡入淡出、柔光过渡，不能影响门的可见性规则。
3. **业务例外**：MRoom2、MRoom3 禁用遮蔽；门本体不被遮住；Boss、剧情和 UI 有明确覆盖规则。

只有当 2D Renderer + Light2D 能复现这三层行为并在移动端性能达标时，才考虑替换当前 Feature。否则保留自定义遮蔽，先把接口和参数 2D 化。

### 8. 水体、特效和 Timeline

水柱、喷水、泉水、Boss、故事开场和结局都使用网格、粒子、三维坐标或 Timeline。转 2D 的关键不是把它们全部改成 Sprite，而是保证：

- 特效的逻辑碰撞和视觉动画分离。
- 粒子、Trail、Line 和动态网格在正交相机下有固定排序。
- Timeline 不直接依赖透视相机或三维距离；镜头用 2D 目标和正交尺寸驱动。
- 特效在房间切换、读档、重生和暂停后能清理并重新初始化。
- Boss 死亡粒子、泉水、门和水面不会因为改 Renderer 而丢失。

### 9. 音频

音乐系统与 3D 不是强绑定，但应趁长期化重构为明确状态机：主菜单曲、Boss 曲、剧情/结局曲保持专用触发；普通背景曲随机播放；一首结束后停 18 秒，再随机下一首；切房、暂停、读档和重生不应把音频状态置于半首无声状态。迁移到 2D 时应保留音频行为测试，不要把音频初始化绑在已删除的 3D 场景对象上。

### 10. UI、输入和移动端

移动端按键、TapTap 胶囊、暂停、重生、地图、行走/奔跑和交互提示都不属于 3D，但相机和安全区变化会影响它们。长期项目必须：

- 统一 PC、Android 和编辑器输入动作名称。
- UI 不使用世界坐标推断屏幕位置。
- 右上角 TapTap 安全区成为禁止放置区域，按钮由安全区布局计算。
- 地图、传送、重生、交互和跑步状态有独立的可见性和可用性条件。
- 所有早期测试字体和临时文字从正式包剔除，避免 2D 美术与旧 UI 混用。

### 11. SDK、构建和包配置

TapTap SDK、成就、隐私协议、Android 包名、签名、正式图标和 PC/Android 输出结构与 3D 无关，应作为发布基线保留。迁移期间必须锁定：

- Android 包名、签名和 Client Token 来源不混用。
- 隐私协议在 APK 中可读且能从 TapTap 测试流程打开。
- 正式图标 `正式ICON.png` 的导入、平台覆盖和最终包图标三处一致。
- PC 包不额外套文件夹、不打进 DonotShip；Android 与 PC 版本号一致。
- 包前清理存档和成就存档，并在包外保存测试用备份。
- 不要因为改成 2D 就删掉仍被 SDK、成就、输入或构建脚本引用的旧资源。

## 四、推荐的迁移顺序

### 阶段 0：冻结和基线

目标：让后续每一步都能证明没有误伤正式关卡。

- 建立迁移分支，记录 `Gaming.unity`、`Gaming_Art.asset`、关键 Prefab、两份旧 JSON、项目设置、PC/Mobile Renderer 的 SHA-256。
- 导出房间、门、传送、Boss、收集品、重生点、移动平台和机制引用清单。
- 记录当前正式包启动、读档、房间切换、传送、重生、Boss 和 TapTap 流程。
- 用隔离场景进行所有试验，禁止在正式 Gaming 上试验自动转换。

### 阶段 1：锁定 2D 产品形态

- 去掉产品入口中的 Perspective3D 模式和按钮。
- 固定正交相机、像素对齐、XY 网格和 Z 排序规范。
- 增加运行时断言：玩家、方块、平台和房间对象的 Z 不能超出允许范围。
- 将相机、UI、输入和渲染设置改为数据化配置。

### 阶段 2：编辑器成为唯一 2D 权威入口

- 完成 Scene overlay 的零写入、对象索引、区域编辑、参数绑定、艺术绘制和 Undo 验收。
- 将旧 PlanningCanvas/JSON 标为导入兼容工具，禁止正常编辑流程回写 JSON。
- 做同格多对象、整区移动、重载、房间重置和正式场景只读审查。

### 阶段 3：2D 兼容层

- 新增统一 `Gameplay2DPlane`、`GridSpace`、`DepthPolicy` 和 `CollisionQuery` 接口。
- 让现有 3D 物理通过接口运行，玩法脚本不再直接散落读取 Z、碰撞体尺寸和投影类型。
- 统一墙、平台、梯子、门、水、收集品和隐藏块的碰撞/视觉图层。

### 阶段 4：按收益选择性迁移物理

推荐顺序：静态墙与普通收集品 → 简单刺和地面 → 门/按钮 → 梯子和单向平台 → 移动平台 → 接触方块和水体 → Boss 与复杂机制。

每一步都需要旧实现与新实现的对照测试，只有在存档、重置、房间切换和移动端通过后才允许替换正式 Prefab。

### 阶段 5：渲染选择

- 若当前自定义 `WorldVisibility` 性能稳定，保留它，仅规范接口和参数。
- 若改用 2D Renderer，先做一个包含墙、门、玩家光照、MRoom2/MRoom3 例外、水体和 Boss 的隔离场景。
- 对 PC 和 Android 分别测 GPU、内存、Draw Call、遮挡边界、白线和像素采样。

### 阶段 6：清理和长期维护

在所有旧存档和正式场景完成迁移后，才清理：3D 相机入口、无用的透视设置、未引用的 3D 物理辅助、重复 JSON、旧编辑器入口和已弃用材质。每次清理都要有引用搜索、反序列化测试和可回滚提交。

## 五、必须建立的自动化验收矩阵

### 数据和编辑器

- 打开/关闭/聚焦/切换模式不改 Scene、Prefab、JSON、Art、Undo、Dirty。
- 绘制、擦除、移动、参数和绑定各自只有一个完整 Undo 组。
- 同一格墙、水、装饰、隐藏块、收集品可共存。
- 整个房间移动后对象、重置归属、艺术归属和机制引用保持。
- Scene 保存、重开、重新加载后所有对象和关系一致。

### 运行时

- 玩家站地、贴墙、梯子、单向平台、头顶通道、搬运和平台载荷。
- 接触方块生长、颜色激活、重力、喷水、水中和重生。
- 收集品拾取、隐藏状态、出入房间、存档、读档和成就。
- 传送只允许已解锁重生点；Boss 入口钥匙/收集品门槛与提示一致。
- Boss 重生点、Boss 死亡、泉水、结局和返回流程。
- MRoom2/MRoom3 光照例外、门始终可见、软遮蔽和房间切换。

### 视觉

- 正交相机在不同分辨率和缩放下像素对齐。
- 墙、梯子、玩家、收集品、隐藏块、前景和水体的层级一致。
- 无移动白线、半像素裂缝、左右描边不一致或材质丢失。
- 普通背景音乐随机播放、曲间 18 秒停顿、专用曲不进入普通随机池。

### 性能

- SceneView 拖动、缩放、刷墙、刷背景、拖动房间和对象列表保持可操作。
- 关卡编辑器和美术编辑器打开不全图重建，不产生隐藏 Dirty。
- 大量未合并白块仍可编辑；合并白块不会改变碰撞和地图结构。
- 首次进入房间、房间切换、读档和移动端启动不出现长帧。
- PC/Android 分别记录 CPU、GPU、内存、GC、Draw Call、Renderer Feature 和物理查询耗时。

### 发布

- Android 在 TapPlay 测试设备启动不闪退，错误日志可导出。
- 隐私协议、TapTap 服务、成就、签名、图标、包名和版本号正确。
- 正式包前清理存档与成就存档，安装后从新存档开始。
- PC 压缩包结构、Android APK/AAB 内容和版本记录可复现。

## 六、迁移中明确不能做的事

1. 不要把 `Gaming.unity` 转成 JSON 再批量生成，正式场景是唯一事实来源。
2. 不要直接把所有 `Rigidbody` 文本替换成 `Rigidbody2D`。
3. 不要直接把所有 `MeshRenderer` 替换为 `SpriteRenderer`。
4. 不要清零所有 Z 坐标；先定义排序策略并逐类迁移。
5. 不要删除 `RoomResetObject`、稳定收集品 ID、Boss 重生点或机制引用。
6. 不要把光照遮蔽当作普通后处理删除；它已经影响玩法可见性。
7. 不要在正式 Gaming 上运行自动转换脚本或编辑器迁移工具。
8. 不要用“能在编辑器里看到”代替“能运行、能重置、能保存、能在 Android 上运行”。

## 七、建议的最终架构

长期项目建议固定为以下边界：

```text
Scene / Prefab / RoomLifecycleManager
        │  唯一权威：房间、真实对象、真实机制引用、重置归属
        ▼
2D Authoring Layer
        │  正交 SceneView、XY 网格、像素对齐、GridArt、Undo
        ▼
2D Gameplay Contract
        │  运动、碰撞、深度、可见性、存档、传送、音频的稳定接口
        ▼
Implementation Adapter
        ├─ 当前阶段：3D Rigidbody / BoxCollider / Mesh / 自定义 URP Feature
        └─ 后续可选：Rigidbody2D / Collider2D / SpriteRenderer / Light2D
```

这样做的核心好处是：产品已经是 2D，设计和编辑器不会再被 3D 模式干扰；但内部实现不必在同一个版本里全部重写。以后若发现某一系统用 2D 物理收益很高，可以只替换该系统的 Adapter，而不会重写整个 Gaming 或存档。

## 八、最终决策建议

建议批准以下决策：

- **现在批准**：长期项目按 2D 产品和 2D 编辑器方向发展；锁正交视图、XY 网格、像素对齐、明确图层和唯一 Scene 权威。
- **现在暂缓**：全面替换 3D 物理、全面切换 2D Renderer、删除所有 Mesh/Transform Z 和清理全部 3D 代码。
- **下一阶段先做**：阶段 0 基线、阶段 1 相机/深度契约、阶段 2 编辑器和 Scene 权威、阶段 3 2D 兼容层。
- **只有通过对照测试才做**：逐系统 2D 物理替换和光照 Renderer 替换。

当前最重要的工程风险不是“项目还残留 3D 类名”，而是多套数据源、碰撞/视觉层混用、房间重置关系和移动端发布流程。先把这些边界固定下来，项目就可以稳定地以 2D 长期维护；之后是否把底层物理也换成 Unity 2D，才是一个可量化、可回滚的技术选择。
